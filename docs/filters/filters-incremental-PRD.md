## 1. 产品目标（一句话）

**让 DokaLike 的滤镜从「8 款固定胶片模拟」升级为「11 参数完整调色引擎 + 用户指定的氛围风格库」，在预览与成片严格一致（所见即所得）的前提下，支持高光/阴影分离、低对比、高饱和这类氛围感调色。**

---

## 2. 背景与问题陈述

### 2.1 现状

- 8 款胶片模拟滤镜（`FilterCatalog`）+ 原图，全部由 4×5 `ColorMatrix` 表达；
- 预览 `ColorFiltered(matrixAt(strength))`，落盘 `FilterPipeline.applyToBytes` 用同一矩阵逐像素 —— **预览与成片完全一致**（这是项目已交付的核心承诺）；
- 强度 0–100% = 恒等矩阵与滤镜矩阵线性插值；
- `assets/luts/` 只有 README，无 PNG；LUT 只在落盘生效，一旦放入即破坏一致性。

### 2.2 问题

用户明确表示**不喜欢现有 8 款的样式风格**，并给出 7 套他想要的风格。根本矛盾是技术路线的不同：

| | 现有 8 款（胶片模拟） | 用户要的 7 套（氛围调色） |
|---|---|---|
| 核心手法 | 全局线性 RGB 变换（矩阵可表达） | 高光/阴影分区 tone curve + 局部对比 + 空间卷积 |
| 观感 | 偏色、整体染色 | 高光阴影分离、低对比、高饱和、通透 |
| 参考系 | 经典负片/反转片 | 手机相册调色、小红书氛围感 |

**这不是换配色能解决的，必须换引擎。**

### 2.3 硬约束（已核实，架构师与工程师直接采信）

| 编号 | 约束 | 说明 |
|---|---|---|
| C1 | 11 参数中当前架构只能实现 6 个 | 曝光 / 对比度 / 色温 / 色调 / 自然饱和度 / 黑点 可做；**高光 / 阴影 / 鲜明度 / 锐度 / 清晰度 做不了** |
| C2 | 预览端是硬瓶颈 | `ColorFiltered` 只能跑矩阵。要做全 11 参数，预览必须换 GLSL shader（`FragmentProgram`） |
| C3 | 性能预算 | 预览 30fps；单帧构图链路 ≤100ms；12MP 落盘滤镜 ≤1.5s（`compute()` 隔离） |
| C4 | 合规 | 纯本地；滤镜命名原创、无商业商标 |
| C5 | LUT 现状 | 无 PNG；LUT 只在落盘生效，放入即破坏一致性 |

### 4.1 P0-16 合规守卫升级 · 完整要求（5 条）

| # | 要求 | 验收标准 |
|---|---|---|
| **①** | 黑名单**哈希化**（离线预计算 `Set<int>` 写死） | 源码与测试**都不含任何商标字符串**，与 P0-14 的 legacy 迁移同一套机制 |
| **②** | 匹配改为 **token 级**（按 `_` / 非字母切分 + camelCase 拆分后逐个哈希比对） | 覆盖 snake_case（`agfa_soft`）与 camelCase（`lutAgfaSoft`）。<br>⚠️ **① 与 ② 是一套机制的两半，不是两个独立要求** —— 不先切分出 token，就无从对 token 取哈希，① 根本无法实现 |
| **③** | **从黑名单移除 `Doka`** | `Doka` / `DokaLike` 是本项目**自有品牌**（全项目约 17 处合法使用）。列入商标黑名单是概念错误：会误杀自家合法命名，且该项永远给不出有意义信号（我们的滤镜名全是中文，纯死逻辑） |
| **④ 新增** | **必须同时检查 `id` 和 `name`** | 现有测试只有 `expect(p.name.contains(tm), isFalse)` —— **只查展示名、从不查 id**。这正是 `agfa_soft` 能存活至今的**直接原因**。新守卫只做哈希化而不扩到 `id`，等于把一个从未生效过的检查换了个实现形式，仍然拦不住 id 侧违规 |
| **⑤** | **中文（CJK）必须保留子串扫描能力**，且 Latin / CJK **统一为「按长度枚举子串 + 哈希」一套机制**（架构师方案，已采纳） | token 级切分对中文**无效**（中文无词边界，`柯达金` 会被切成一整个 token，永远不匹配 `柯达` 的哈希）。<br>统一结构：`Map<int /*字符数*/, Set<int> /*哈希*/>`，对候选名枚举相同长度的连续子串逐个哈希比对。<br>对 Latin，子串是 token 的**严格超集**（任何 token 都是子串），所以一套机制同时覆盖 `agfa_soft` 与 `lutAgfaSoft`，**不需要分支**；且与现有 `contains` 语义等价，不会像纯 token 化那样丢失检测能力。<br>⚠️ **但见下方 ⑤-a 的裁剪约束** |

**⑤-a 子串表的裁剪约束（⚠️ 必须遵守，否则会复活已修掉的误报）**

`portra` **不得进入子串表**。实测：`portrait` 的长度 6 子串包含 `portra`（`'portrait'[:6] == 'portra'`）—— 这正是我们在 §9.5 用 `\bportra\b` 消灭的那个误报。**统一子串机制会把它带回来**：一旦守卫的扫描面从 `id`/`name` 扩到变量名、注释或 enum 值，`FilterCategory.portrait` / `_portraitIds` / `ShootMode.portrait` 就会被判违规。

→ **裁剪原则：每个守卫层的词表必须与该层的敏感度匹配。**

| 层 | `portra` 是否入表 | 理由 |
|---|---|---|
| 第 1 层 grep | ✅ 保留（`\bportra\b` + `portra[_0-9-]`） | 有词边界保护，不会误伤 `portrait`，同时能抓 `portra_400` |
| 第 2 层守卫（子串表） | ❌ **移除** | 无边界保护，必然误伤 `portrait` |

当前范围内（只扫 `id`/`name`）不会立刻误报，但这是**被安放的陷阱**：它只在有人扩大扫描面时才爆炸，而那时没人会想起这条。**现在就摘掉。**

**§9.6-a 变异用例的自证（递归层）**：变异用例**本身也必须先自证它会失败**。如果注入的样本实际不会触发守卫，这条测试就会「该失败却通过」—— 它反而**制造了 §9.6 想消灭的那种虚假安全感**。

> 实例（PM 自纠）：曾提议注入 `lutDokaSample` 作为 camelCase 变异样本，但 `Doka` 已于 P0-16 ③ 从黑名单删除 —— 守卫不会报错，该变异用例形同虚设。已改为 `lutFujiSample`。

**§9.6-b 变异样本的选取原则**：必须选用**词表中不可能被裁剪的核心项**（`fuji` / `kodak` / `agfa` / `柯达`），**不得选用有争议或可能被移出的项**（如 `Doka`）。否则词表一变动，测试就从"会失败"退化为"永远通过"，且不报错。

**守卫的变异用例必须覆盖三条独立路径**（每条都需通过 §9.6-a 自证），缺一则该路径未被验证：

| 注入 | 必须触发 |
|---|---|
| `portra_400` 这类 snake_case id | 第 1 层 grep 报错（**注意**：按 ⑤-a，`portra` 已移出第 2 层子串表，本条由 grep 层承担） |
| `lutFujiSample` 这类 camelCase 变量名 | 子串扫描报错 |
| `柯达金` 这类中文展示名 | CJK 子串扫描报错（**注意**：若日后把某个词移出子串表，对应的变异用例必须同步复核，否则它会静默退化成"永远通过"） |

## 5. 11 参数定义表

> iOS 相册术语对齐：**鲜明度 = Brilliance，清晰度 = Definition，自然饱和度 = Vibrance**。

| # | 中文名 | 参数 key | 对应算子 | UI 取值 | 归一化 | 当前可实现 | 备注 |
|---|---|---|---|---|---|---|---|
| 1 | 曝光 | `exposure` | 线性光域乘性增益 `out = in · 2^EV` | -100 ~ +100 | `EV = (v/100) × kEv`，默认 `kEv = 1.0` | ✅ 可做 | **必须在 linear 域施加**，sRGB 域直接乘会导致观感与相册不一致（见 §10-R3） |
| 2 | 鲜明度 | `brilliance` | 亮度自适应曲线（提中暗部、保护高光）+ 轻微饱和联动 | -100 ~ +100 | `v/100` | ❌ **不可做** | 非线性 tone curve，矩阵无法表达 |
| 3 | 高光 | `highlights` | 亮度分区 tone curve，只作用于 `L > ~0.5` 区域 | -100 ~ +100 | `v/100` | ❌ **不可做** | 需亮度掩码 + 平滑过渡带，避免分区边界出现硬边 |
| 4 | 阴影 | `shadows` | 亮度分区 tone curve，只作用于 `L < ~0.5` 区域 | -100 ~ +100 | `v/100` | ❌ **不可做** | 同上 |
| 5 | 对比度 | `contrast` | 围绕中灰线性拉伸 `out = (in − 0.5)·k + 0.5` | -100 ~ +100 | `k = 1 + v/100 × kContrast`，默认 `kContrast = 0.6` | ✅ 可做 | 钳制到 [0,1] |
| 6 | 黑点 | `blackPoint` | 暗部基准平移（+ = 压暗最暗部使画面更深邃；− = 提亮暗部产生灰雾） | -100 ~ +100 | `v/100` | ✅ 可做 | 结果单调、黑场不为负 |
| 7 | 自然饱和度 | `vibrance` | **仅提升低饱和像素**的饱和度，保护高饱和与肤色 | -100 ~ +100 | `v/100` | ✅ 可做（近似） | 矩阵域为**全局饱和度近似**，丢失"保护高饱和"特性；shader 域应升级为真 vibrance |
| 8 | 色温 | `temperature` | 白平衡偏移：正 = 暖（R↑ B↓），负 = 冷（R↓ B↑） | -100 ~ +100 | `v/100` | ✅ 可做 | 幅度系数待真机对标相册标定 |
| 9 | 色调 | `tint` | G ↔ M 偏移：**正 = 洋红（Magenta），负 = 绿（Green）** | -100 ~ +100 | `v/100` | ✅ 可做 | 方向需真机对标相册校验（见 §11-6） |
| 10 | 锐度 | `sharpness` | 高频 USM 卷积（小半径、小量） | -100 ~ +100 | `v/100` | ❌ **不可做** | 空间卷积；落盘端 12MP 逐像素性能风险最高（见 §10-R1） |
| 11 | 清晰度 | `definition` | 中频局部对比（半径大于锐度，增强轮廓/质感） | -100 ~ +100 | `v/100` | ❌ **不可做** | 局部对比，需邻域/模糊金字塔 |

**统计：可做 6 个（曝光 / 对比度 / 黑点 / 自然饱和度 / 色温 / 色调），不可做 5 个（鲜明度 / 高光 / 阴影 / 锐度 / 清晰度）。**

### 5.1 工作域划分（混合域）与算子顺序

**域划分（决定）：**

| 域 | 参数 | 理由 |
|---|---|---|
| **linear 域** | 曝光、色温、色调 | 物理正确（曝光是光量倍增、白平衡是色温偏移），符合 §10-R3 |
| **感知域（sRGB 编码值）** | 鲜明度、高光、阴影、对比度、黑点、自然饱和度 | 锚点按上表的 `0.5` 中灰语义定义，最贴近手机相册手感 |

> 全 linear 域（对比度锚点改 0.18、分区阈值重算）列为 **P1 备选**：真机 A/B 对标相册时若混合域观感明显偏离，则整体切换并重新标定。域的选择不是不可逆决策 —— 标定常数集中在 `FilterTuning`，改数字即可。

**算子顺序（P0 硬要求）：**
混合域下各算子**不可交换**（先做曝光还是先做对比度，结果不同）。因此：

1. 算子顺序必须**单一定义**（放在 tune/engine 的共享处），**预览（shader）与落盘（Dart）必须逐算子同序**；
2. 顺序属于**一致性验收项**，不是实现细节 —— 两端顺序不一致直接判定 P0-4 不通过。

### 5.2 分辨率无关性（锐度 / 清晰度）

锐度与清晰度是**空间算子**，其效果天然依赖分辨率 —— 若半径用绝对像素定义，12MP 成片的锐化会明显强于 1080p 预览，一致性不可能达标。

**要求：**
1. **锐度与清晰度统一走标准尺度** —— 两个算子共用同一个整数 `rBase`、同一套采样点、同一个尺度，而不是「清晰度走标准尺度、锐度走原生归一化」。这样一致性论证只有一条，锐度的落盘成本也同步下降；
2. 两者的**半径按「相对图像长边的比例」定义**，不用绝对像素；
3. **空间算子层统一在一个标准尺度上计算（长边 = 1080，与预览同尺度），再把增量应用回全分辨率** —— 预览与落盘**按构造一致**，且 12MP 的计算代价降为 1080p 量级（性能问题一并解决）；
4. 预览端与落盘端**必须使用同一标准尺度常量**，不得各自定义；
5. **尺度必须由「图像的渲染长边」推导，不能由图层尺寸推导**（见下面 D-5）。

> **关于「12MP 锐化由标准尺度上采样得到、略柔」**：这不是缺陷。本项目「所见即所得」的基准定义就是**成片 = 预览**，预览本身就是标准尺度，因此标准尺度下的观感**就是基准观感**，不存在另一个 ground truth。但需在 P1 阶段用 9.1-A 的 A/B 图确认在最大锐度（`+16`，丁达尔）下无可察觉劣化。

**D-5（陷阱，架构师发现）**：现有 UI 中 `CameraPreview` 是 **scale-to-cover + ClipRect**（屏幕竖屏而图像 4:3），因此**图层尺寸（如 1080×2400）≠ 图像实际渲染尺寸**。若 shader 直接拿图层尺寸换算作用尺度，结果是错的。因此：
- shader 必须被**显式告知图像的渲染长边**；
- 9.1-A 的调试 harness 必须**去裁剪 + contain 完整渲染 + 固定长边 = 1080**，否则两端尺度不同、比对无意义。

**注意**：`长边 / 短边 / sqrt(w·h)` 三种尺度口径**只在 aspect 固定时等价**。一旦 aspect 不同（真机 cover 场景）即分叉 —— 所以 harness 的「固定长边」要求不能省。

## 6. 归一化规则

### 6.1 参数量纲

假设用户给的数值为 **iOS 相册式整数区间 `[-100, +100]`，0 = 中性**（依据：用户给出的值全部落在 −100 ~ +100 且大量出现 ±100 边界，符合整数滑块的行为特征）。

### 6.2 映射规则

```
UI 整数 v ∈ [-100, 100]  ──►  引擎内部 v_norm ∈ [-1.0, +1.0]

v_norm = clamp(v / 100.0, -1.0, +1.0)
```

### 6.3 强度缩放

```
全局强度 s ∈ [0, 1]（UI 显示 0–100%）
有效参数 v_eff = v_norm × s
```

**为什么强度作用于参数向量而不是输出像素**：这是唯一能同时保证 `s=0` 严格等于原图、`s=1` 严格等于满参数的做法，且与现有「恒等矩阵与滤镜矩阵线性插值」的语义保持连续（旧 8 款的行为不因此改变）。

### 6.4 标定常数（可调，默认值见下表）

| 常数 | 默认 | 含义 | 需标定原因 |
|---|---|---|---|
| `kEv` | 1.0 | 曝光 ±100 对应的 EV 数 | 相册实际范围需真机对标（见 §11-7） |
| `kContrast` | 0.6 | 对比度 ±100 的拉伸强度 | 避免 ±100 时出现严重溢出 |
| `kTemperature` / `kTint` | 待定 | 色温/色调幅度 | 与相册观感对齐 |
| `hlSplit` | 0.5 | 高光/阴影分区阈值（归一化亮度） | 分区边界位置 |
| `hlSoftness` | 0.15 | 分区过渡带宽度 | 防止出现硬边 |

> 以上常数集中在 `AppConstants`（项目约定：禁止魔法数字散落），不允许散落在 shader 或 pipeline 里。

## 8. 七个关键问题的明确答复（本文核心价值）

### Q1：「曝光 +100 … 曝光调回 0」怎么处理？

**答复：最终曝光 = 0，前面的 +100 视为无效中间态，不产生任何残留影响。**

**理由（三条，按说服力排序）：**

1. **手机相册的参数模型是「状态机」不是「操作序列」。**
   iOS 相册的每个调色项是一个**最终标量**，不是累加器。滑块从 +100 拖回 0，该参数的状态就是 0，渲染管线读到的就是 0。不存在"操作历史逐条重放"的语义。
2. **用户自己写了「调回 0」，说明他知道最终要的是 0。**
   「先拉满看细节再调回」是调参过程中的**观察手段**（曝光拉满时暗部细节可见，便于配高光/阴影/黑点），不是要保留的效果。他是把操作过程复述给了 PM。
3. **若保留 +100，会与同一套风格内的其他参数自相矛盾。**
   浮光跃金同时要「高光 −100」「对比度 −30」；丁达尔同时要「高光 −81」「鲜明度 +50」。这些是**压动态范围、做柔和氛围**的取向。而曝光 +100 是全画面 +1 EV 的提亮，会把本该被压下去的中间调重新顶回来，与"低对比氛围感"直接打架。三套风格里有两套（浮光跃金、丁达尔）是**强暖调**，曝光 +100 叠加色温 +100 / +80 会大面积溢出到死白。

**处理动作：**
- 参数表按**曝光 = 0** 填写（已体现在 §7.2）；
- 但这是**高影响判断**（3 套风格观感会完全不同），因此同时安排 **P1-5：为浮光跃金 / 霜蓝 / 丁达尔各出「曝光=0」与「曝光=+100」两版对比图**，交用户拍板；
- 参数表数据驱动，用户拍板后**改一个数字即可切换**，无需改代码。

### Q2：参数范围归一化

**答复：假设为 iOS 相册式整数区间 `[-100, +100]`，0 为中性；映射到引擎内部 `[-1.0, +1.0]` 浮点。**

- 依据：用户给出的值全部落在 −100 ~ +100，且频繁出现 ±100 边界（色温 +100 / −100、高光 −100、曝光 +100），这是整数滑块被拖到底的典型特征，而非 0~1 或 0~255 量纲。
- 规则：`v_norm = clamp(v / 100.0, -1.0, +1.0)`；强度缩放 `v_eff = v_norm × s`。
- 各参数在引擎内部再由标定常数换算为算子实际量（EV、对比度系数、卷积强度等），标定常数集中在 `AppConstants`。细节见 §5 / §6。

### Q3：术语对齐（中文 → 算子）

**答复：采用 iOS 相册术语映射。**

| 中文 | 英文 | 算子 | 说明 |
|---|---|---|---|
| 鲜明度 | **Brilliance** | 亮度自适应 tone curve（提中暗部、保护高光）+ 轻微饱和联动 | ❌ 不是 Vibrance |
| 自然饱和度 | **Vibrance** | 只提升低饱和像素的饱和度，保护高饱和与肤色 | ❌ 不是 Brilliance |
| 清晰度 | **Definition** | **中频**局部对比（大半径，增强轮廓/质感） | 与锐度区分在频率 |
| 锐度 | **Sharpness** | **高频** USM 空间卷积（小半径） | 与清晰度区分在频率 |
| 高光 | **Highlights** | 亮度分区 tone curve（亮部掩码） | |
| 阴影 | **Shadows** | 亮度分区 tone curve（暗部掩码） | |
| 黑点 | **Black Point** | 暗部基准平移 | 不是"亮度" |
| 曝光 | **Exposure** | linear 域乘性增益 | |
| 对比度 | **Contrast** | 中灰锚点线性拉伸 | |
| 色温 | **Temperature** | R↔B 偏移 | 正 = 暖 |
| 色调 | **Tint** | G↔M 偏移 | **正 = 洋红，负 = 绿**（待真机校验） |

> **鲜明度 vs 自然饱和度**是最容易搞混的一对：鲜明度管**明暗层次**，自然饱和度管**色彩浓度**。用户 7 套里两者经常同时出现且取值不同（如郁郁葱葱：鲜明度 −27 / 自然饱和度 +26 —— 柔化明暗但加浓色彩），证明是两个独立旋钮，工程师不得合并实现。

### Q4：「拍雪花」是拍摄参数不是滤镜 —— 做还是不做？

**答复：不做为滤镜。拆为两级，明确放弃不可行的 3 项。**

**技术事实（已核实项目代码）：**
- `camera ^0.11` 暴露的能力只有：`setExposureOffset` / `setZoomLevel` / `setFocusMode` / `setExposureMode` / `setFlashMode`；
- **无 ISO、无快门速度、无白平衡接口**；Android CameraX 侧也未暴露手动 Sensor 控制。

**取舍建议：**

| 处置 | 内容 | 优先级 |
|---|---|---|
| ✅ 做 | **变焦 3× + 单次自动对焦** → 封装为「雪景拍摄」快捷预设（技术上可行） | P1-6 |
| ✅ 做 | **拍摄参数提示卡**：以只读文案展示用户给的 5 条参数原文，不可做的 3 条明确标注「本设备不支持，请在专业模式/手动 App 中设置」 | P1-6 |
| ❌ 放弃 | **ISO 50 / 快门 1/640 / WB 4000K** —— `camera` 插件无接口，需自写双端原生通道（Android CameraX + iOS AVFoundation），成本与收益严重不匹配，且会破坏"极简"定位 | 明确不做 |
| 🔁 转做 | **P2：`初雪` `first_snow` 后期风格** —— 用后期参数近似"雪景通透"观感（提阴影 + 冷色温 + 降饱和 + 增清晰度），这才是在本项目能力圈内的解法 | P2-2 |

**为什么不硬做 ISO/快门**：本项目定位是"极简轻量 AI 相机"，手动曝光控制属于专业相机 App 范畴；为 3 个参数写双端原生通道会引入大量平台分支代码，与"56 个 Dart 文件、纯 Dart 引擎"的现有架构风格冲突。

### Q5：「园林电影」没有参数 —— 怎么办？

**答复：做。由 PM 代填一套初始值，标注「待校准」，随 P1-5 对比图一并请用户拍板。**

**理由：**
1. 风格名语义足够明确 ——「园林」= 绿植、低饱和、冷调；「电影」= 低对比、有质感、保留高光细节。这两个词的组合指向清晰，代填的风险可控。
2. 不做空壳 —— 一个没有参数的滤镜条目在滤镜栏里是纯粹的负体验（点了没反应或点了是原图）。
3. 成本极低 —— 参数表是数据驱动的，代填 11 个数字，不满意改数字即可。

**代填值**：曝光 0 / 鲜明度 +20 / 高光 −35 / 阴影 +25 / 对比度 −25 / 黑点 +15 / 自然饱和度 +10 / 色温 −15 / 色调 +10 / 锐度 +10 / 清晰度 +20（见 §7.2-⑦）。

**兜底**：若用户在 P1-5 拍板环节表示"先别做"，则从 `FilterCatalog.all` 移除，滤镜栏变为 6 套新风格，不影响引擎改造。

### Q6：现有 8 款胶片滤镜怎么处理？

**答复：全部保留，但不主推 —— 分组 + 新组优先。**

**理由（三条）：**
1. **用户说"不喜欢"，没说"删掉"。** 删除是不可逆决策，而"不喜欢"是偏好陈述。保留的成本很低（它们已经能用且一致），删除的机会成本很高。
2. **删除会破坏已拍照片的元数据。** `PhotoRepository` 用 Hive 持久化照片元数据，其中含 `filterId`。删除预设后 `FilterCatalog.byId()` 会静默回退到 `original`，导致相册里历史照片的滤镜名显示错误 —— 这是一个用户可见的数据回归。
3. **保留 = 风险隔离。** 旧 8 款继续走**矩阵路径**（`ColorFiltered`），新 7 套走 **shader 路径**。两条路径解耦，即使 shader 在真机出问题，旧滤镜完全不受影响，App 不会整体回退到"没滤镜"。

**具体方案：**

| 项 | 处置 |
|---|---|
| 滤镜栏 | 分两段：「氛围」（7 套新风格，在前）+「经典」（原图 + 旧 8 款，在后）。**原图保持在首位**（现有行为不变） |
| 旧 8 款实现路径 | **不变**，继续 4×5 矩阵 + `ColorFiltered`，效果与改造前逐像素一致（P0-9 回归基线） |
| 旧 8 款分类 | 保持现有 `film` / `portrait` / `landscape` / `night` / `mono`（与新增的 `mood` 区分） |
| AI 推荐 | 推荐池含全部 16 款，**同分时 `mood` 组排在前面**（P1-2） |
| 后续 | 若 3 个版本内「经典」组使用率为 0，再评估下线 |

### Q7：强度滑杆怎么办？

**答复：主路径保留全局强度滑杆（0–100%）；P1 增加二级「参数微调面板」。**

| | 方案 A：每参数单独可调（11 根滑杆） | **方案 B：全局强度（1 根）+ 二级微调面板**（采纳） |
|---|---|---|
| 与"极简"定位 | ❌ 冲突。11 根滑杆 = 专业调色 App，与项目"极简、轻量、打开即拍"的核心定位直接矛盾 | ✅ 主界面保持 1 根滑杆 |
| 手机屏可用性 | ❌ 11 根滑杆需要全屏面板，破坏"取景器为主"的布局 | ✅ 主界面无变化，微调是**按需进入**的二级页 |
| 改造成本 | 高（状态模型、持久化、UI 全改） | 低（强度语义从"矩阵插值"升级为"参数向量缩放"，持久化字段不变） |
| 专业用户需求 | ✅ 满足 | ✅ P1 二级面板满足 |

**具体决策：**

1. **全局强度（P0）**：语义升级为 `v_eff = v_norm × s`（§6.3）。`s=0` 严格等于原图，`s=1` 严格等于满参数。持久化字段 `strength` 不变，冷启动恢复逻辑不变。
2. **默认强度**：7 套新风格默认 **100%**（用户给的参数即最终值）。
3. **参数微调面板（P1）**：选中滤镜后通过入口进入，展示该滤镜 11 个参数滑杆，实时反映到预览；关闭后恢复。**只读展示也是价值** —— 用户能看到这套风格"为什么长这样"，符合"可解释"的产品调性。
4. **另存为我的滤镜（P2）**：面板调整结果可命名保存。

## 9. 验收标准

### 9.1 所见即所得（核心）

> **两级验收**。架构师指出：预览输入是相机实时流、成片输入是 JPEG 解码，两者**本身就不是同一份数据**（快门瞬间自动曝光/白平衡还会变化）。因此拆成两级，**只有 A 级是 P0 通过条件**。

#### 9.1-A 静态图同路径比对（**P0 通过条件**，隔离变量，只测滤镜链路）

**测试方法：**
1. 准备 **3 张标准测试图**：① 灰阶卡 / 色卡（检验 tone curve 与色偏）② 户外人像（检验肤色与 vibrance）③ 风光（检验绿色/天空分区与卷积）；
2. **同一张静态图**分别喂进「预览渲染路径」与「落盘渲染路径」，各施加**每一套新风格 × 强度 {50%, 100%}**；
   > 需要一个能把静态图喂进预览渲染路径的 **QA / 调试入口**（可测试性要求，请工程师提供）。
3. 采集两端输出，按 §9.2 方法对齐后逐像素比对。

**通过阈值：**

| 指标 | 阈值 | 说明 |
|---|---|---|
| 平均绝对误差 **MAE** | **≤ 6 / 255**（约 2.4%） | 全图所有通道 |
| 95 分位误差 **P95** | **≤ 12 / 255** | 排除 5% 最差像素 |
| 最大单点误差 **Pmax** | **≤ 25 / 255** | 允许边缘/高频区域 |
| 平均色差 **ΔE\*ab** | **≤ 5** | 无色偏的客观判据（ΔE≤5 为"可接受"级别） |
| 主观评审 | **3 名评审一致认为"看不出差别"** | 在标准观图环境下并排对比 |

**测试矩阵：** 3 张测试图 × 7 套风格 × 2 个强度 = **42 组**，× 双端（iOS / Android）= **84 组**，全部需通过。

#### 9.1-B 真实拍摄端到端比对（**不设 P0 通过条件**，回归基线 + 人工判断）

真实取景 → 快门 → 成片，抓取**快门瞬间的最后一帧预览**与成片比对。

- **阈值放宽**：MAE ≤ 12/255、ΔE\*ab ≤ 10（因为快门瞬间的 AE / AWB 变化是系统行为，不是滤镜链路的缺陷）；
- **不设为 P0 通过条件** —— 超出阈值时先人工判断是否 AE/AWB 抖动导致，是则记录不判失败；
- **但必须记录**：这个数字就是用户真实感知的落差，是"所见即所得"的对外口径，每版回归都要跑并留档。

### 9.2 比对的三个必要前置处理（不做则比对无效）

1. **统一像素网格**：成片是 12MP，预览约 1080p。锐度/清晰度是**分辨率相关**的算子，全分辨率下锐化观感天然更强。比对时**必须把成片降采样到预览分辨率**再逐像素比对 —— 用户感知的是"整体观感"而非像素级的高频差异。（若 §5.2 的「清晰度层标准尺度」落地，本条自动满足，但仍保留作为兜底校验。）
2. **统一编码**：预览截屏是无损 PNG，成片是 `quality=92` JPEG。比对前**必须对预览图也做一次 `encodeJpg(q=92)` 再 decode**，否则测的是 JPEG 压缩差异而不是滤镜差异。（quality 复用 `AppConstants.jpegQuality`，不要写死 92。）
3. **统一工作空间与算子顺序**：两端必须在**同一工作空间**（按 §5.1 的混合域划分）且**逐算子同序**。工作空间不一致会直接污染 ΔE；顺序不一致则整条链路语义不同，直接判 P0-4 不通过。

**两层的已知局限（必须写清楚，别假装它是完备的）：**
1. `\bportra\b` 抓不到 `portra_400` 这类 snake_case（因为 `_` 属于正则词字符），用追加项 `portra[_0-9-]` 补上；同类问题对 `agfa` 不存在（未加 `\b`，裸匹配即可同时命中 `agfa_soft` 与 `lutAgfaSoft`）；

### 9.6 验收项敏感性自证（通用原则）

**原则：每条验收项必须自证「它是会失败的」。** 一条不可能失败的检查等于没有保护 —— 它只会给出虚假的安全感。

**§9.6-a（递归层）变异用例自身也要自证。** 如果注入的样本实际不会触发断言，这条测试就「该失败却通过」，反而制造本章想消灭的虚假安全感。
*实例：camelCase 变异用例不可用 `lutDokaSample` —— `Doka` 已被 P0-16 ③ 移出黑名单，守卫不会报错。改用 `lutFujiSample`。*

**§9.6-b 变异样本的选词原则。** 只用词表中**不可能被裁剪的核心项**（`fuji` / `kodak` / `agfa` / `柯达`），不用有争议或可能被移出的项。否则词表一变动，测试即从"会失败"退化为"永远通过"且不报错。

（由架构师的算子顺序三层保障提炼，推广到全部关键验收项。）

| 验收项 | 自证方式 |
|---|---|
| 算子顺序一致（P0-4） | ① 交换任意两步，断言输出**必须不同**（证明顺序确实不可交换）；② **变异测试**：故意颠倒一步，断言探针**必须报错** |
| 合规守卫（P0-6 / P0-16） | 变异测试必须覆盖**三条独立路径**（见 §4.1）：① snake_case 商标 id → 报错；② camelCase 商标变量名 → 报错；③ 含中文商标的展示名 → 报错。**只做其中一条，另外两条路径等于未被验证。**<br>⚠️ 每条变异用例还需通过 **§9.6-a 自证**（它自己也会失败）与 **§9.6-b 选词原则**（只用核心项，不用可能被裁剪的项） |
| 一致性探针（P0-4） | 变异测试：故意让落盘与预览差一个参数，断言指标**必须超阈值** |
| 强度恒等性（P0-1） | 判据里写死「误差必须为 0」，天然自证 |

### 10.1 LUT 的最终定位（约束 C5 的答复）

**决策：LUT 通道废弃（deprecated），本次改造后不再作为滤镜实现手段。**

**理由：**
1. **11 参数模型已是完整的调色表达**，LUT 是另一种（烘焙好的、参数不可调的）表达。两套并存会让"所见即所得"的验证面**翻倍**（每条路径都要单独验证一致性），收益为 0。
2. LUT 与"强度滑杆""参数微调"天然冲突 —— LUT 是烘焙结果，无法按强度平滑插值到恒等，也无法单参数微调。
3. shader 统一处理后，LUT 若要保留必须走 shader 采样，增加复杂度但不增加任何用户价值。

**执行动作（P0-13）：**

| 文件 | 动作 |
|---|---|
| `lib/models/filter_preset.dart` | `lutAsset` 字段标记 `@Deprecated('LUT 通道已废弃，调色统一由 11 参数引擎实现')` |

| `lib/services/filter_pipeline.dart` | LUT 分支代码**保留但恒不触发**（因为无 PNG）；加注释说明废弃状态 |
